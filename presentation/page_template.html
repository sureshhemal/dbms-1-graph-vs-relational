Fraud detection: tables or graphs?

The same synthetic fraud dataset, loaded into Neo4j, Memgraph and MySQL, asked thirteen questions in two parts. Part 1 asks about records: fetch, filter, total, rank. Part 2 asks about the links between records, which is where fraud shows up. For each question: the problem, the query in each engine, what changes between them, the answer, and how long it took.

Method

    Read the numbers with these in mind

    • Memgraph runs in Docker inside a Colima VM (4 CPUs, 8 GiB) and is reached through a forwarded port. Neo4j and MySQL run natively on macOS. That setup costs Memgraph something on every query.
    • Every engine runs its default configuration, with the indexes created by the loaders. Nothing was tuned per query.
    • MySQL's buffer pool was raised from the 128 MB default to 2 GB, so the whole 560 MB transactions table and its indexes sit in memory, as the graph engines' data does.
    • G4 on MySQL uses idx_tx_client and then reads each matching row back from the table to check type and global_step. A covering index on (client_id, type, global_step, to_client_id) would very likely narrow the gap.
    • One laptop, warm caches. These numbers compare query shapes on this machine; they are not a general benchmark.
